# ml/conversion: CLIP ViT-B/32 (default) and MobileCLIP-S0 (fallback) to Core ML

Reproducible conversion of a CLIP image encoder and text encoder to Core ML, a PyTorch-vs-Core-ML parity check, and
the text-encoder / tokenizer decision for the iOS app. No weights, `.mlpackage` files, vocab/merges files or
checkpoints are committed (they are gitignored); everything is regenerated by the scripts here.

**Default model: OpenCLIP ViT-B/32, `laion2b_s34b_b79k`, MIT licence.** MobileCLIP-S0 stays as a documented fallback
(research-only licence, see the last section). The Swift side picks the model from a `model_config.json` next to the
compiled models and defaults to the MobileCLIP-S0 values when that file is absent
(`ios/Recall/Sources/MLEncoders/ModelConfig.swift`).

### Produce it

```bash
cd ml/conversion
./setup.sh                        # python3.11; creates ml/.venv, installs pins, downloads + sha256-verifies the checkpoint and 3 sample images
source ../.venv/bin/activate
python convert_openclip.py        # -> build/clip-vit-b32/{CLIP_ViT_B32_Image,CLIP_ViT_B32_Text}.mlpackage + model_config.json
python export_tokenizer.py        # -> build/tokenizer/{vocab.json,merges.txt}, golden_tokens.json (+ self-check vs open_clip)
python parity_openclip.py         # open_clip vs Core ML: cosines, zero-shot sanity, timing (exit 1 if min cosine <= 0.99)
./install_models.sh               # = install_models.sh clip-vit-b32 ../../ios/Recall/Resources build/clip-vit-b32
```

`install_models.sh [MODEL] [DEST] [SRC]` takes `clip-vit-b32` (default) or `mobileclip-s0`, a destination resource
root (default `ios/Recall/Resources`) and a source folder (default `build/clip-vit-b32`, or `build` for MobileCLIP).
It removes the other model's packages and a stale `model_config.json` from the destination.

Pins: `requirements.txt` (direct dependencies) and `requirements-openclip.lock.txt` (full `pip freeze` of the
environment that produced the numbers below; torch 2.7.0, coremltools 9.0, open_clip_torch 3.3.0). Conversion needs
`torch.backends.mha.set_fastpath_enabled(False)`: the eval fast path of `nn.MultiheadAttention` traces to
`_native_multi_head_attention`, which coremltools 9.0 does not implement.

### Tokenizer

Same CLIP BPE as before, so `export_tokenizer.py`, the Swift `CLIPTokenizer` and `golden_tokens.json` are unchanged.
Checked for this model: the repo's own `merges.txt` equals our merge list line for line (48,894 merges); its
`vocab.json` has 49,408 entries and the identical token-to-id map except that the two special tokens are spelled
`<|startoftext|>`/`<|endoftext|>` instead of `<start_of_text>`/`<end_of_text>` (ids 49406/49407 in both);
`open_clip.get_tokenizer("ViT-B-32")` reproduces all 11 golden id lists. The real-vocab Swift tests passed against
the generated files.

### Measured results (this Mac, not a phone)

Machine: macOS 27.0.1, arm64 Apple Silicon, Python 3.11, coremltools 9.0, torch 2.7.0, fp16 models. Full output in
[`parity_output_openclip.txt`](parity_output_openclip.txt).

- **Parity, `compute_units=CPU_ONLY`:** images (n=14: 2 synthetic + 3 photos, each full frame plus 3 derived crops, so
  only 3 independent photos) cosine(open_clip, Core ML) min 0.998186, mean 0.999281; phrases (n=14) min 0.999890,
  mean 0.999953. With `compute_units=ALL`: images min 0.999949, mean 0.999992; phrases min 0.999999, mean 0.999999.
  The Core ML image path is fed PIL bicubic resize + crop, open_clip uses its torchvision transform, so image
  cosines mix fp16 error with a small preprocessing difference; I did not separate them.
- **Zero-shot sanity (3 photos, not an accuracy measure):** the tiger photo scores 0.300 for "a tiger" against

- **Swift, real models** (`testRealCoreMLModelsRankTigerPhotoAsCatNotDog`, Swift tokenizer, `ModelLocator` compile,
  real runners, `compute_units=.all`): tiger photo vs "a photo of a cat" 0.2026, "a photo of a dog" 0.1518,
  "a photo of a car engine" 0.0625.
- **Swift preprocessing at 224 vs PIL/torchvision** (`Resize(224, BICUBIC)` + `CenterCrop(224)`, 10 images: 4 synthetic,
  3 photos, 3 detector-style crops): mean absolute pixel difference **0.000** on all ten (the old bilinear path was
  0.969 to 12.446). Core ML embeddings of Swift-preprocessed vs PIL-preprocessed inputs: cosine 1.00000 on all ten.
- **Timing on THIS Mac** (arm64 Apple Silicon, macOS 27.0.1, coremltools `predict()` including Python marshalling,
  fp16, median of 30 warm runs after 2 warm-ups): `CPU_ONLY` image 6.2 ms (p95 7.7), text 4.5 ms (p95 6.5);
  `ALL` image 7.6 ms (p95 11.3), text 4.3 ms (p95 5.0). **Phone latency is not measured**, nor is thermal behaviour.

### Switching encoder family (rule)

CLIP ViT-B/32 and MobileCLIP-S0 both output 512-d unit vectors, so the dimension checks in `Memory` and `Retrieval` accept
a mix, but vectors from the two families are not comparable, and saved tracks carry no encoder identity. After a switch,
old tracks would stay rankable against new queries and new observations would fail to associate or duplicate tracks,
silently. **Rule: every switch of family, in either direction and including the fallback, requires clearing the phone's
saved object memory and world maps first. Delete the Recall app from the phone (that removes its container), then install
and run the new build.** `install_models.sh` enforces the cheap half: it refuses to replace one family's packages with the
other's unless you pass `--memory-cleared`, and it prints the reminder on every install (it cannot see the phone). Tagging
embeddings with an encoder identity so the app can invalidate them itself would be the proper fix; it touches the stored
track format and `docs/03_CONTRACTS.md`, so it is not done here (needs a `[DECISION]`).

(Original note:) the HF card says `apple-amlr`, while Apple's
separate `apple/coreml-mobileclip` card says `apple-ascl` with a link to `LICENSE_weights_data` in
ml-mobileclip. The [AMLR terms](https://huggingface.co/apple/MobileCLIP-S0/blob/main/LICENSE) limit use
and model derivatives to research purposes and exclude product development. Do not assume a demo or
prototype qualifies; a human must review the terms before using or relying on the checkpoint or converted
models. Do not redistribute converted weights from this repo (they are gitignored).

Why S0: smallest of the family (S0/S1/S2/B), the plan only needs open-vocabulary retrieval over a
few dozen household crops, and phone heat/latency matter (plan 3.5). Alternatives: Apple also
publishes ready-made Core ML packages at <https://huggingface.co/apple/coreml-mobileclip> (S0, S1, S2,
BLT image and text). We convert ourselves so the pipeline and preprocessing are auditable; the
published packages are the fallback if conversion breaks on a newer toolchain. MobileCLIP2 exists
(`apple/MobileCLIP2-S0`, same `apple-amlr` card) but was not evaluated.

### Text-encoder route (plan section 4.4): decision (applies to both models)

**On-device Core ML text encoder + a small Swift port of the CLIP tokenizer with bundled vocab/merges
(route 2). The `/embed_text` Mac endpoint (route 3) is not needed.**

Reasons:
- The text encoder converts and matches PyTorch (cosine >= 0.99998 on 7 phrases, see below), so the
  fallback endpoint is unnecessary and the demo keeps working with no network path to the Mac.
- I inspected `ml-stable-diffusion`'s `BPETokenizer.swift` (route 1). It exists and loads
  `merges` + `vocabulary` files, but its default pad token is `<|endoftext|>`, while MobileCLIP/open_clip
  pad with id `0`, and I did not verify its handling of digits (open_clip splits digits one by one).
  Taking the SPM dependency for ~80 lines of logic we can test ourselves is not worth the risk.
  If someone wants it anyway, feed it the same `vocab.json`/`merges.txt` and compare to `golden_tokens.json`.

### Tokenizer plan for Swift (applies to both models)

Bundle two files in the app (generated, not committed; `python export_tokenizer.py` writes them to
`build/tokenizer/`): `vocab.json` (49,408 entries, token string -> id, ~0.9 MB) and `merges.txt`
(48,894 merge pairs in rank order, one `a b` per line, ~0.5 MB). Both derive from the OpenAI CLIP
vocabulary shipped in `open_clip`'s `bpe_simple_vocab_16e6.txt.gz`.

Loading: parse `vocab.json` with `JSONDecoder` into `[String: Int]`; parse `merges.txt` into
`[Pair: Int]` where the rank is the line index. Algorithm (the Python reference in
`export_tokenizer.py::encode` is the spec and matches open_clip exactly on all golden cases):

1. Collapse whitespace runs to one space, trim, lowercase.
2. Split with the regex `<start_of_text>|<end_of_text>|'s|'t|'re|'ve|'m|'ll|'d|\p{L}+|\p{N}|[^\s\p{L}\p{N}]+`
   (note `\p{N}` is a single digit per token).
3. For each piece: UTF-8 bytes -> GPT-2 byte-to-unicode map -> characters; mark the last char with
   `</w>`; repeatedly merge the lowest-rank adjacent pair until none is in the merge table; map each
   resulting symbol through `vocab.json`.
4. Output `[49406] + ids.prefix(75) + [49407]`, zero-padded to 77, as `MLMultiArray` `int32 [1,77]`.

Known gap: open_clip also runs `ftfy.fix_text` and `html.unescape` first; the port skips them (typed or
speech-to-text English phrases are unaffected, mojibake input would differ).
`golden_tokens.json` (10 phrases incl. empty, punctuation, digits, over-length) is committed so a
Swift unit test can assert exact id equality.

Query embedding per plan 4.6: encode `phrase` and `"a photo of " + phrase`, average, re-normalise.

cd ml/conversion

Reproducibility: `setup.sh` verifies the checkpoint and all three sample images by sha256 (the script fails on
a mismatch). `requirements.txt` pins every direct dependency to the version used for `parity_output.txt`;
`requirements.lock.txt` is the full `pip freeze` of that environment. The output below was captured after a fresh
conversion and parity run on 2026-10-17 (macOS 27.0.1 arm64, Python 3.11) using the pinned environment and
already-present, hash-verified model and sample assets. The setup/download step was not repeated for that run.

Notes on versions: torch 2.14.1 failed inside coremltools 9.0 on the image encoder
(`TypeError: only 0-dimensional arrays can be converted to Python scalars`), torch 2.7.0 (the newest
version coremltools 9.0 lists as tested) works. `mobileclip` is installed with `--no-deps` because its
metadata asks for torch >= 2.8; it runs on 2.7.0 here.

To use in the app: `./install_models.sh mobileclip-s0` (this also removes any `model_config.json`, so the Swift defaults of
256 px apply); Xcode compiles the packages to `.mlmodelc` at build time.

### Measured results (fallback)

Machine: macOS 27.0.1, arm64 (Apple Silicon), Python 3.11, coremltools 9.0, torch 2.7.0,
`compute_units=CPU_ONLY`, fp16 model. Full output in [`parity_output.txt`](parity_output.txt).

- Text: cosine(PyTorch, Core ML) 0.999982 to 0.999988 over 7 phrases.
- Image: 0.998419 to 0.999961 over 5 images (2 synthetic, 3 public sample photos). Lowest are the
  real photos (~0.9984). The Core ML path is fed a PIL bicubic resize+crop while PyTorch uses
  torchvision's transform, and the model is fp16, so this mixes fp16 error with a small
  preprocessing difference; I did not separate the two.
- Sanity: on the 3 sample photos, `data/dog.jpg` scores highest on "a tiger" (0.282 vs 0.046 to 0.145 for
  other phrases) and the two cat photos score highest on "a cat" (0.132 and 0.166). Despite its name,
  `dog.jpg` is the Siberian tiger photo (sha256 `2ae007fb...`, from `mishig/sample_images/tiger.jpg`); the original
  run saved it under that name and `setup.sh` keeps it so `parity_output.txt` row labels stay valid. That is 3 images, a smoke test, **not an
  accuracy measure**. Retrieval accuracy and the 0.85 association threshold must be calibrated on the
  real eval set (`docs/04_EVALS.md`).
- Package sizes on disk (`du -sh`): image 22 MB, text 81 MB (fp16).
