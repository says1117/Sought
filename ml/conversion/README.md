# ml/conversion: MobileCLIP-S0 to Core ML (T-009)

Reproducible conversion of a MobileCLIP image encoder and text encoder to Core ML, a PyTorch-vs-Core-ML
parity check, and the text-encoder / tokenizer decision for the iOS app. No weights or `.mlpackage`
files are committed (they are gitignored); everything is regenerated by the scripts here.

## Chosen model

| Item | Value |
|---|---|
| Model | MobileCLIP-S0 (`mobileclip_s0`), Apple |
| Checkpoint | `mobileclip_s0.pt` from <https://huggingface.co/apple/MobileCLIP-S0>, sha256 `809b408eff74f8058843e86a1f92967097d42ba782450e85b8f4867b7f0ca0b7` |
| Model code | <https://github.com/apple/ml-mobileclip> pinned at `48faa0fea4b08d74188b3841771aca6ff2c92852` |
| License (verified from the HF API card and the `LICENSE` file in the HF repo) | `apple-amlr`, text at <https://huggingface.co/apple/MobileCLIP-S0/blob/main/LICENSE> |
| Image input | 256 x 256 RGB, `scale=1/255`, **no mean/std** (matches MobileCLIP's own transform: Resize 256, CenterCrop 256, ToTensor) |
| Text input | `int32 [1, 77]` CLIP BPE ids (`49406` start, `49407` end, padded with `0`) |
| Embedding dim | 512, L2-normalised inside both Core ML graphs |
| Core ML format | `mlprogram`, iOS 17 target, fp16 weights/compute (`--precision fp32` available) |

**License caveat for the human (not resolved by me):** the HF card says `apple-amlr`, while Apple's
separate `apple/coreml-mobileclip` card says `apple-ascl` with a link to `LICENSE_weights_data` in
ml-mobileclip. The AMLR text describes the model as released for scientific research purposes. Read it
before any use beyond the hackathon demo, and do not redistribute converted weights from this repo
(we do not: they are gitignored).

Why S0: smallest of the family (S0/S1/S2/B), the plan only needs open-vocabulary retrieval over a
few dozen household crops, and phone heat/latency matter (plan 3.5). Alternatives: Apple also
publishes ready-made Core ML packages at <https://huggingface.co/apple/coreml-mobileclip> (S0, S1, S2,
BLT image and text). We convert ourselves so the pipeline and preprocessing are auditable; the
published packages are the fallback if conversion breaks on a newer toolchain. MobileCLIP2 exists
(`apple/MobileCLIP2-S0`, same `apple-amlr` card) but was not evaluated.

## Text-encoder route (plan section 4.4): decision

**On-device Core ML text encoder + a small Swift port of the CLIP tokenizer with bundled vocab/merges
(route 2). The `/embed_text` Mac endpoint (route 3) is not needed.**

Reasons:
- The text encoder converts and matches PyTorch (cosine >= 0.99998 on 7 phrases, see below), so the
  fallback endpoint is unnecessary and the demo keeps working with no network path to the Mac.
- I inspected `ml-stable-diffusion`'s `BPETokenizer.swift` (route 1). It exists and loads
  `merges` + `vocabulary` files, but its default pad token is `<|endoftext|>`, while MobileCLIP/open_clip
  pad with id `0`, and I did not verify its handling of digits (open_clip splits digits one by one).
  Taking the SPM dependency for ~80 lines of logic we can test ourselves is not worth the risk.
  If someone wants it anyway, feed it the same `vocab.json`/`merges.txt` and compare to `golden_tokens.json`.

## Tokenizer plan for Swift

Bundle two files in the app (generated, not committed; `python export_tokenizer.py` writes them to
`build/tokenizer/`): `vocab.json` (49,408 entries, token string -> id, ~0.9 MB) and `merges.txt`
(48,894 merge pairs in rank order, one `a b` per line, ~0.5 MB). Both derive from the OpenAI CLIP
vocabulary shipped in `open_clip`'s `bpe_simple_vocab_16e6.txt.gz`.

Loading: parse `vocab.json` with `JSONDecoder` into `[String: Int]`; parse `merges.txt` into
`[Pair: Int]` where the rank is the line index. Algorithm (the Python reference in
`export_tokenizer.py::encode` is the spec and matches open_clip exactly on all golden cases):

1. Collapse whitespace runs to one space, trim, lowercase.
2. Split with the regex `<start_of_text>|<end_of_text>|'s|'t|'re|'ve|'m|'ll|'d|\p{L}+|\p{N}|[^\s\p{L}\p{N}]+`
   (note `\p{N}` is a single digit per token).
3. For each piece: UTF-8 bytes -> GPT-2 byte-to-unicode map -> characters; mark the last char with
   `</w>`; repeatedly merge the lowest-rank adjacent pair until none is in the merge table; map each
   resulting symbol through `vocab.json`.
4. Output `[49406] + ids.prefix(75) + [49407]`, zero-padded to 77, as `MLMultiArray` `int32 [1,77]`.

Known gap: open_clip also runs `ftfy.fix_text` and `html.unescape` first; the port skips them (typed or
speech-to-text English phrases are unaffected, mojibake input would differ).
`golden_tokens.json` (10 phrases incl. empty, punctuation, digits, over-length) is committed so a
Swift unit test can assert exact id equality.

Query embedding per plan 4.6: encode `phrase` and `"a photo of " + phrase`, average, re-normalise.

## Reproduce

```bash
cd ml/conversion
./setup.sh                      # needs python3.11; creates ml/.venv, installs pins, downloads checkpoint + 3 sample images (sha256-verified)
source ../.venv/bin/activate
python convert.py               # -> build/MobileCLIP_S0_Image.mlpackage, build/MobileCLIP_S0_Text.mlpackage
python export_tokenizer.py      # -> build/tokenizer/{vocab.json,merges.txt}, golden_tokens.json (+ self-check vs open_clip)
python parity.py                # PyTorch vs Core ML cosines (exit 1 if min cosine <= 0.99)
```

Reproducibility: `setup.sh` verifies the checkpoint and all three sample images by sha256 (the script fails on
a mismatch). `requirements.txt` pins every direct dependency to the version used for `parity_output.txt`;
`requirements.lock.txt` is the full `pip freeze` of that environment. A fresh `./setup.sh && python convert.py &&
python parity.py` on 2026-10-17 (macOS 15.0 arm64, Python 3.11) reproduced `parity_output.txt` row for row.

Notes on versions: torch 2.14.1 failed inside coremltools 9.0 on the image encoder
(`TypeError: only 0-dimensional arrays can be converted to Python scalars`), torch 2.7.0 (the newest
version coremltools 9.0 lists as tested) works. `mobileclip` is installed with `--no-deps` because its
metadata asks for torch >= 2.8; it runs on 2.7.0 here.

To use in the app: copy `build/*.mlpackage` into `ios/Recall/Resources/Models/` (gitignored); Xcode
compiles them to `.mlmodelc` at build time.

## Measured results

Machine: macOS 15.0, arm64 (Apple Silicon), Python 3.11, coremltools 9.0, torch 2.7.0,
`compute_units=CPU_ONLY`, fp16 model. Full output in [`parity_output.txt`](parity_output.txt).

- Text: cosine(PyTorch, Core ML) 0.999981 to 0.999988 over 7 phrases.
- Image: 0.998426 to 0.999966 over 5 images (2 synthetic, 3 public sample photos). Lowest are the
  real photos (~0.9984). The Core ML path is fed a PIL bicubic resize+crop while PyTorch uses
  torchvision's transform, and the model is fp16, so this mixes fp16 error with a small
  preprocessing difference; I did not separate the two.
- Sanity: on the 3 sample photos, `data/dog.jpg` scores highest on "a tiger" (0.281 vs 0.046 to 0.145 for
  other phrases) and the two cat photos score highest on "a cat" (0.132 and 0.165). Despite its name,
  `dog.jpg` is the Siberian tiger photo (sha256 `2ae007fb...`, from `mishig/sample_images/tiger.jpg`); the original
  run saved it under that name and `setup.sh` keeps it so `parity_output.txt` row labels stay valid. That is 3 images, a smoke test, **not an
  accuracy measure**. Retrieval accuracy and the 0.85 association threshold must be calibrated on the
  real eval set (`docs/04_EVALS.md`).
- Package sizes on disk (`du -sh`): image 22 MB, text 81 MB (fp16).
